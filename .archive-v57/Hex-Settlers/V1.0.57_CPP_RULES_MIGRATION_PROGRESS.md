# Hex Settlers V1.0.57 — C++ rules-engine migration (verified tranche)

## Important status: NOT a complete C++ server migration

The request is to rebuild the entire JavaScript game engine in C++, use it in
browser play (via WebAssembly), and validate with 100 full games. The supplied
server is approximately 16,330 lines of JavaScript, with intertwined game
rules, account/security, persistence, lobby/room protocol, AI, scenario
builders, clocks, and asynchronous multiplayer transitions. It is not safe to
replace that with an incomplete port or call test *snapshots* “100 games.”

This release **adds a real compiled C++ deterministic rules core**, validates
its present operations against their authoritative JavaScript counterparts,
and includes a **separate 100-real-game regression runner** for the unchanged
JavaScript multiplayer engine. It does **not** route gameplay, training, or
browser interactions through the new C++ core. The previous neural trainer,
CUDA-production subset, GPU controls, web assets, and Cloudflare deployment
code remain in place.

## New native C++ operations

In `native/hex-core/`:

* Player resource totals and required discards.
* Cost affordability for roads, ships, settlements, cities, and development cards.
* Per-player longest road computation (including roads and ships, blocked
  by opponents' buildings).
* Longest Road title ownership and existing-title-holder tie/departed-player
  behavior.
* Largest Army title ownership and its tie/departed-player behavior.
* VP totals: settlement, city, development VP, new-island VP, Through the
  Desert bonus, Longest Road, Largest Army; win-target threshold.
* `settlementDistanceOk()` and `edgeConnectsToPlayer()` legality helpers.
  Note that `edgeConnectsToPlayer()` intentionally checks **roads** but not
  ships, exactly as the existing JavaScript function does.

This work uses a little-endian `int32_t` C ABI (`hex_rules_core.hpp`) to allow
future in-process native bindings and WASM reuse. `hex_cpp_step(State*)` is
purposefully stateless. It does not load or run whole games yet.

The earlier `scripts/cuda-exact/` port remains unchanged: resource production
and normalized bank-trade mutation, but not complete game rules.

## Windows: verify the native core

1. Back up `neural_ai_model.json` and `scripts/output` before replacing files.
2. Merge this release over your Hex Settlers source; keep your existing
   trained model and checkpoints.
3. Open **x64 Native Tools Command Prompt for VS 2022** in the project root.
4. Execute:

```cmd
native\hex-core\Build-Core-Windows.cmd
```

The command compiles `hex_rules_runner.exe` and compares 100 deterministic
board states to **the actual server.js rule functions**. To expand coverage:

```cmd
node native\hex-core\core_parity.js --count 1000
node scripts\cuda-exact\exact_parity.js --backend cpu --count 1000
npm run test:neural
```

## Windows: run **100 complete matches** in the existing engine

This test is a JavaScript **baseline** (not a native-C++-game test). It needs a
working `npm ci` and a functioning Node.js server.

1. Open a command prompt in the project root and run `npm ci`.
2. Double-click `Validate-100-Full-Games.cmd`, or run:

```cmd
npm run test:games:100
```

The command launches 100 real, headless, rules-enforced AI matches, covering
all 19 standard trainer templates for 4, 6, and 8 players, including New
Shores. Test Builder is excluded. A completed report must contain 100 unique
finished games, legitimate victories, matching model-update counters, and at
least one finished game per scenario. The test rejects incomplete coverage or
incomplete training receipts.

It **does not modify your original trained weights**. Its model copy,
checkpoints, logs, and JSON report are at
`scripts/output/validation-100/`. An interrupted run can be resumed by
launching the command again. It may take a substantial amount of time and
may reveal existing AI stalls; that is important regression evidence.

The 100-game report is authoritative only for the existing JS server. The
full C++ engine does not exist yet, so full-game JS-vs-C++ differential
validation cannot yet be performed.

## WebAssembly preparation

Use the **Emscripten SDK** (`emcc`) to compile the deterministic C ABI:

```cmd
native\hex-core\Build-WASM.cmd
```

The result is `hex_rules_core.js` and `.wasm` in `native/hex-core/`. This is a
build target only, **not** automatically loaded by the web game. In-process
WASM calls may accelerate heavy computation, but small calls can be slower
than optimized JavaScript once conversion/copy costs are included. Benchmark
before switching browser gameplay; compiling C++ alone does **not** imply
CUDA GPU use or higher browser FPS.

## What remains before a safe production switch

* Translate complete board setup, all Classic/Seafarers scenarios (including
  Fog Island, New Shores, 5–6 and 7–8-player variants), ports, fog revelation,
  layout generation, seeded randomness and legal action enumeration.
* Translate setup turn order, robber/pirate, gold-choice queues, trades,
  development card acquisition/play/limits, road/ship placement and moves,
  scoring, cards, winning, surrender/disconnect, and all other turn-state
  transitions.
* Design a versioned state/action ABI and a deterministic canonical serializer
  that covers **all** game state, not just current test fields.
* Replay real JavaScript game logs through both engines, diffing the full
  state after **every action**, including adversarial/fuzzed traces.
* Run 100+ complete matches on the new native engine **and** JavaScript with
  matched seeds, action logs and final state hashes on every scenario.
* Independently validate the WASM implementation in supported browsers;
  performance benchmark, add graceful fallback and staged opt-in rollout.
* Preserve server-side authoritative legality. Browser WASM cannot be trusted
  to authorize moves; it only accelerates local predictions/UX unless a native
  server adapter is deployed and independently verified.

Do not replace the deployed `server.js` with the currently incomplete kernel.
