# Hex Settlers V1.0.47 — persistent Discord configuration and account linking

## Deploy target and version

- Release: **V1.0.47**. The existing version incrementing/stamping algorithms are unchanged.
- Production Worker: `hex-settlers`
- Production R2 bucket: `hex-settlers-state` (unchanged)
- Discord Activity hostname: `activity.hexsettlers.org` (unchanged)
- The `public/discord-activity.bundle.js` client and its SHA-256 checksum are **already bundled** in this release.

## Why the Discord client ID disappeared

Wrangler deployments normally replace dashboard-managed nonsecret environment variables with the `vars` recorded in the Wrangler config. V1.0.46 omitted `DISCORD_CLIENT_ID` from `wrangler.container.production.jsonc`, so a deployment could remove the dashboard setting even though it had existed previously.

V1.0.47 fixes this two ways:

1. `wrangler.container.production.jsonc` includes `"keep_vars": true`, which preserves other dashboard-managed variables on deployment.
2. Its `vars` explicitly includes `"DISCORD_CLIENT_ID": "1477895334406656101"`. This identifier is public and safe to commit. The Discord client secret and bot token must **not** be committed.

**Important:** Configure `DISCORD_CLIENT_SECRET`, `DISCORD_BOT_TOKEN`, and `OAUTH_STATE_SECRET` as Worker **Secrets** in Cloudflare, and keep existing provider credentials configured. Wrangler retains Worker secrets on deployment, but it does not manufacture missing ones.

## New login and account linking

1. On the web/Activity login page, check **Link to existing account**.
2. Choose any of **Email/password, Google (Gmail), GitHub, Cloudflare, Discord**.
3. Sign in to an **existing Hex Settlers player account** with its password or with a provider that is **already linked** to that account.
4. After login, the **Link your sign-in methods** dialog shows the chosen methods and which ones are already connected. Click **Connect** beside a provider to authorize it; for email/password, choose **Manage email login** to complete verified email/password setup. These links do not merge player IDs or stats.
5. Click **Done · Continue to game** when finished.

If a player signs in with a provider identity that is **not linked to any Hex Settlers account**, the OAuth callback takes the player to the **Create your account** screen with a clear explanation. The player can create a new account with that provider (CAPTCHA required), create an email/password account, or return to login with an already-linked method before connecting the new provider.

Never link provider accounts based only on matching email, username, or Discord display name. If a provider identity is **already owned by another** Hex Settlers user, the server refuses to attach it to a different player. An intentional merge must use the authenticated administrative account-merge procedure after checking ownership. Automated silent merges are not allowed.

The selection is kept in the browser session across OAuth redirects. It is not sent as proof of account ownership. Provider linking remains server-validated and tied to a currently active authenticated session, with OAuth PKCE/state protection.

When the login originated in a Discord Activity, selected methods are copied into the secure website handoff, and the one-time Discord login approval is completed **before** the provider-linking dialog appears.

## Cloudflare and Discord setup to verify

1. Cloudflare Dashboard → Workers & Pages → `hex-settlers` → Settings → Variables and Secrets: verify the public Client ID `1477895334406656101` and **Secret** values `DISCORD_CLIENT_SECRET`, `DISCORD_BOT_TOKEN`, and `OAUTH_STATE_SECRET` are available.
2. Discord Developer Portal → Hex Settlers → OAuth2 → Redirects: confirm both `https://127.0.0.1` (Activity) and `https://hexsettlers.org/api/auth/oauth/discord/callback` (website) are listed, exactly.
3. Keep the existing Activities URL mapping `/` → `activity.hexsettlers.org`.
4. Deploy using the existing production config, **not staging**:
   ```sh
   npm run build:discord && npm install --prefix cloudflare --no-audit --no-fund && node scripts/stamp-git-build.cjs
   ./cloudflare/node_modules/.bin/wrangler deploy --config wrangler.container.production.jsonc
   ```
5. Run `node scripts/verify-discord-bundle.cjs`. Do not exclude `public/discord-activity.bundle.js` or its checksum from Git.
6. Test a player with one linked method, a player linking a second method, an unrecognized OAuth identity routed to registration, existing-provider ownership conflicts, and login security limits. Test with two Discord users in the Activity.

**No migrations, account deletion, R2 bucket changes, or manual merge of player data are required.** This release does not change the account storage format.

## Notes

- An unknown password login continues to return a generic authentication error to avoid exposing whether a username/email exists. Only a **verified OAuth provider subject** can trigger the specific unlinked-provider registration route.
- The existing two-failure CAPTCHA threshold, five-failure/20-minute password lockout, and MFA-protected admin login are unchanged.
- Any user account already linked to a provider remains linked. Existing provider identities are never replaced without a deliberate unlink.
- The official Discord Activity and external OAuth logins require live testing in your deployment. Local tests cannot simulate provider approval or Cloudflare secrets end-to-end.
