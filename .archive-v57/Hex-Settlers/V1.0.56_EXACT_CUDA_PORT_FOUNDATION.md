# Hex Settlers V1.0.56 — Native CUDA exact-rules port foundation

## Important: full game engine NOT yet ported

This is a **partial native CUDA reimplementation**, not a CUDA version of the 16,330-line `server.js` or a 20,000-real-game GPU simulator. The existing authoritative JavaScript CPU self-play workflow remains intact. No exact GPU whole-game speedup, VRAM saturation or production equivalence is claimed. The abstract CUDA arena is separate and must not train the authoritative model as if its games were real.

CUDA cannot directly run Node.js/JavaScript. An exact GPU engine requires rebuilding the authoritative state machine and all scenario rules in native/GPU code, using deterministic reproducibility and CPU-vs-GPU parity at *every action boundary*. The port must not silently replace rules with approximations.

## What is implemented

- `scripts/cuda-exact/hex_exact_common.h` — native state schema and deterministic, shared host/device transition logic.
- `scripts/cuda-exact/hex_exact_cpu.cpp` — independently compiled CPU native engine for exact-state reference tests.
- `scripts/cuda-exact/hex_exact_cuda.cu` — real NVIDIA CUDA kernel, one native game-state transition per GPU thread, with explicit device memory and synchronization.
- `scripts/cuda-exact/exact_parity.js` — reads **the authoritative functions out of the actual `server.js`** and compares random game states and native results for 4–8 players. It rejects any field mismatch.
- `Build-Exact-CPU.cmd` and `Build-Exact-CUDA.cmd` — Windows build-and-verify launchers.

The covered deterministic transitions are:

1. **Dice resource production**, preserving tile order, node/corner order, settlement/city yields, robber-blocked opportunities, bank-shortage partial grants, virtual Gold Fields, and queued per-player Gold Field tile IDs. The game state/geometry is already prepared; rolling dice is outside this kernel.
2. **Normalized bank-trade inventory mutations**, including the authoritative server's give-then-take ordering, bank inventory limits, insufficient-hand / insufficient-bank rejection. Raw user-input normalization and port trade-ratio legality are **still performed by JavaScript**, not by the GPU.

The native state format is fixed-width and currently supports up to eight players, 256 tiles, six corners per tile and 32-bit integer counts. Unsupported shapes fail validation; there is no silent approximation.

The GUI includes hardware telemetry, real allocated VRAM versus total VRAM, estimated CUDA optimizer VRAM, advanced watchdog/search/restart controls and an exact-rule parity button. The parity button does **not** start GPU full-game training.

## Windows: build and validate on your RTX 3090 Ti

1. Back up `neural_ai_model.json` and `scripts/output` before merging this release. Training models/checkpoints are not replaced.
2. Install **Visual Studio 2022 Desktop development with C++** and **NVIDIA CUDA Toolkit** appropriate to your driver. PyTorch alone does not provide `nvcc.exe`.
3. Open **x64 Native Tools Command Prompt for VS 2022** if the CUDA Toolkit compiler is not on `PATH`.
4. From the extracted `Hex-Settlers` folder, run:

   ```bat
   scripts\cuda-exact\Build-Exact-CPU.cmd
   scripts\cuda-exact\Build-Exact-CUDA.cmd
   ```

   Each script compiles the corresponding binary and runs 500 state comparisons against `server.js` immediately. A failure **does not** activate the GPU as a trusted game simulator.

5. Double-click `Start-Neural-Trainer.cmd`. In **Native CUDA parity**, select **NVIDIA CUDA kernel** and run 250–2000 checks. Hardware telemetry comes from `nvidia-smi`. CUDA optimization for existing self-play is configured separately in the GUI.

6. For normal training, start a short 20–50-game CPU-authoritative self-play job with CUDA learning acceleration. Only once successful, start larger runs. The model is not altered by a parity check.

## Current rule-coverage boundary

**Not yet moved to CUDA:** all map/scenario generators and fog reveal transitions; turn ordering, setup, paired turns, public/private lobbies, all player-trade negotiation, ports and raw trade validation, roads/ships/cities/settlement placement and adjacency legality, dev-card deck/actions, robber/pirate movement and steals, 7-roll discards, long-road graph traversals, Largest Army, score/victory transitions, AI action generation, and complete game end state. Only porting both the rules and their AI state-machine integration will permit a full authoritative GPU self-play label.

An accurate full port should be delivered in multiple independently verifiable milestones: board encoding and generation parity -> exact legal-action enumeration -> all phase transitions -> all scenarios and features -> AI decision/weight compatibility -> full matched deterministic games -> CUDA throughput tuning. Do not tune for peak VRAM occupancy until each stage passes rule parity; memory allocation by itself does not imply GPU work or simulation speed.

## Existing tests and safety

```powershell
npm ci
npm run test:neural
npm run build:bootstrap
```

V1.0.56 native CPU parity exercised 480 randomized state comparisons and the neural suite passed 24 tests in the build environment. The native CUDA kernel has **not** been compiled or executed on an NVIDIA GPU in the build environment; `nvcc` and CUDA hardware were absent. It must pass on your PC before any CUDA performance claims can be made.

### Notes on performance and VRAM

The native test snapshot is 26,296 bytes per game. A 10,000-state CUDA batch requires about **251 MiB** for input and another **251 MiB** for output, plus CUDA context, temporary allocations and driver overhead. That is **test snapshot allocation**, not a memory estimate for complete GPU games. The GUI intentionally labels this separately from the PyTorch optimizer's VRAM estimate. Saturating 24 GB of VRAM is not an optimization goal; throughput, parity, SM occupancy and time per *correct* game are the relevant metrics.
